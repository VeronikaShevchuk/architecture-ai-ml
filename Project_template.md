# Исследование моделей и инфраструктуры

**Наша цель** — выбрать наиболее подходящий, безопасный и экономически эффективный стек технологий для создания внутреннего RAG-бота. Решение должно учитывать конфиденциальность данных (финско-эстонская компания с жесткими требованиями к Data Governance), существующий разрозненный ландшафт документации (Confluence, PDF, GitHub) и потребности различных групп пользователей.

## Сравнение LLM-моделей (локальные vs облачные)

|Критерий|Локальные модели (Hugging Face)|Облачные модели (OpenAI / YandexGPT)|
|--------|----------|-----------|
|Качество ответов|Зависит от модели. Современные открытые модели показывают результаты, приближающиеся к проприетарным, юособенно на специализированных задачах после дообучения.|Очень высокое, особенно у GPT-4 и его аналогов. Модели хорошо понимают сложные контексты и генерируют связные, релевантные ответы "из коробки".|
|Скорость работы|Зависит от мощности GPU. На выделенном GPU (например, NVIDIA L4 или A10) можно добиться высокой скорости инференса, сопоставимой с облачными решениями|Зависит от загрузки серверов провайдера и сетевой задержки. Обычно стабильно высокая, но может быть "хвост" задержек (p95/p99) в пиковые часы|
|Стоимость владения|Высокие первоначальные затраты на оборудование (сервер с GPU) и его обслуживание. В долгосрочной перспективе, при высоких нагрузках, может быть экономически выгоднее облака.|Оплата по факту использования (за токены). Для небольшой компании с несколькими сотнями сотрудников это может быть дешевле, чем покупка собственных GPU. Однако, при росте нагрузки счета могут стать непредсказуемыми|
|Конфиденциальность|Полный контроль над данными. Критически важное преимущество для QuantumForge, так как данные (включая чертежи, спецификации, кодовую базу) не покидают периметр компании.|Данные отправляются на сервера провайдера. Это может противоречить политикам безопасности и регуляторным требованиям (GDPR, SOC 2), особенно для финско-эстонской компании|
|Удобство развертывания|Требует квалифицированной команды для настройки инфраструктуры (установка драйверов, библиотек, оптимизация модели), управления зависимостями и мониторинга|Крайне простое. Получение API-ключа и интеграция через несколько строк кода. Не требует забот об оборудовании.|

## Сравнение моделей эмбеддингов (локальные vs облачные)

|Критерий|Локальные эмбеддинги (Sentence-Transformers)|Облачные эмбеддинги (OpenAI Embeddings)|
|--------|----------|-----------|
|Скорость создания индекса| Высокая, особенно на GPU. Можно векторизовать все ~21 000 документов компании (18k Markdown + 3k Confluence + 250 PDF) за разумное время, используя пакетную обработку|Зависит от скорости сети и лимитов API. При большом объеме данных процесс может занять много времени и потребовать управления очередями.|
|Качество поиска| Современные модели, такие как BAAI/bge-base-en-v1.5 или intfloat/e5-mistral-7b-instruct, показывают результаты, сопоставимые или даже превосходящие OpenAI Embeddings на многих бенчмарках, особенно в условиях гибридного поиска|Очень высокое. Модель text-embedding-3-large отлично понимает семантику текста и контекст.|
|Стоимость владения|Бесплатны после развертывания на собственной инфраструктуре. Требуют только ресурсов сервера.|Прямые затраты на каждый вызов API. При большом объеме запросов и необходимости периодического перестроения индекса (например, ежемесячно) затраты могут стать значительными.|

## Сравнение векторных баз данных (ChromaDB vs FAISS)

|Критерий|FAISS (Facebook AI Similarity Search)|ChromaDB|
|--------|----------|-----------|
|Скорость поиска|Высокая, особенно на GPU. Оптимизирован для работы с индексами, которые полностью помещаются в оперативную память. Является отраслевым стандартом для эффективного поиска по сходству|Высокая, но может немного уступать FAISS на очень больших наборах данных, так как является полноценной базой данных с дополнительными функциями.|
|Скорость индексации|Быстрое построение индекса, особенно при использовании GPU.|Также быстрая. Процесс векторизации и добавления документов интуитивно понятен.|
|Сложность внедрения|Низкая. Это библиотека, а не серверная БД. Легко интегрируется в Python-код с LangChain, что идеально подходит для старта и выполнения данной проектной работы|Низкая. Является клиент-серверной базой данных, но также имеет простой Python API и отлично интегрируется с LangChain. Легко поднимается в Docker.|
|Поддержка и удобство|Не имеет встроенного клиент-серверного взаимодействия, не поддерживает метаданные "из коробки" (хотя в LangChain эта абстракция добавляется). Подходит для случая, когда индекс хранится на диске и загружается в память приложением.|Более "тяжелое" решение с собственным сервером, поддержкой метаданных, фильтров и мониторинга. Лучше подходит для многопользовательских сценариев, где важна персистентность и управление данными.|
|Стоимость владения|Минимальная. Не требует отдельного сервиса или инфраструктуры. Работает в том же процессе, что и ваше приложение.|Низкая. Можно запустить как отдельный контейнер в docker-compose, что потребляет дополнительные, но небольшие ресурсы.|

## Рекомендуемая конфигурация сервера

Учитывая необходимость обработки конфиденциальных данных и объем информации (~21k документов, ежемесячный прирост 400 страниц), рекомендуется гибридный или локальный подход.

Базовая конфигурация для RAG-системы (инференс + поиск):
- CPU: 8-16 ядер (современный Intel Xeon или AMD EPYC). Достаточно для работы приложения, FAISS и preprocessing.
 - RAM: 32-64 GB. Необходимо для хранения индекса FAISS в памяти (индексы эмбеддингов могут быть довольно объемными) и для работы приложения.
- GPU: Критически важен. Для обеспечения быстрого инференса LLM и, опционально, для ускорения построения индекса эмбеддингов. Рекомендуется NVIDIA GPU с 16-24 ГБ VRAM, например:
    - NVIDIA RTX A4000 / A5000 (для рабочей станции)
    - NVIDIA L4 / A10 (для серверного форм-фактора)
    - NVIDIA RTX 3090/4090 (бюджетный вариант для старта)
- Диск: 500 GB - 1 TB NVMe SSD. Для хранения базы знаний (исходные документы), индексов, кэша моделей и логов.
- Сеть: Доступ в интернет для загрузки моделей с Hugging Face (только на этапе настройки). Внутренняя сеть 1 Гбит/с.

Эта конфигурация позволит запустить модели с отличной производительностью и полным контролем над данными.

## Выводы

Для выполнения данной задачи (создание прототипа бота) предлагается использовать локальный стек (Вариант 1) с векторной базой данных FAISS.

**Почему FAISS?**

- Простота: Это библиотека, а не серверная БД. Ее легко установить (pip install faiss-cpu) и интегрировать с LangChain, что идеально для быстрого старта.

- Скорость: FAISS обеспечивает молниеносный поиск по сходству, что критично для RAG-пайплайна.

- Ресурсы: Не требует запуска отдельного сервиса в Docker, экономя ресурсы на этапе разработки и тестирования.

    # RAG-бот с техниками Few-shot и Chain-of-Thought

## Описание
RAG-бот для фантастического мира "Хроники Сумеречного Легиона" с применением современных техник промптинга.

## Техники промптинга

### 1. Few-shot prompting
В промпт добавляются 1-2 примера вопросов и ответов из той же предметной области:
- "Кто такой Архивариус?" → пример ответа
- "Что случилось на Парке Встреч?" → пример ответа

### 2. Chain-of-Thought (CoT)
Бот явно показывает свою цепочку рассуждений:
1. Анализ запроса
2. Поиск в контексте
3. Проверка наличия информации
4. Формирование ответа

### 3. Обработка отсутствия информации
Если информация не найдена, бот отвечает "Я не знаю"
